# 四维评分

## 分数怎么给

每一维 0.0–4.0，一位小数。四维相加，总分 0.0–16.0。

| 分 | 含义 |
|---|---|
| 0.0 | 完全没提到 |
| 1.0 | 提到了，但只是一个词，没有展开 |
| 2.0 | 说了，但笼统，听的人只能猜 |
| 3.0 | 完整、能听懂，但缺细节或因果 |
| 4.0 | 充分，且有具体细节支撑 |

中间值按程度取：3.2 是「基本完整、有一处含糊」，2.6 是「大致说了，但关键处不清」。

**不要给整数凑整。** 全给 3.0 说明你没在分辨。

## 四维定义（按框架对应）

### PREP

| 维 | 看什么 |
|---|---|
| 观点清晰 | 有没有一句能单独拿出来当结论的话；立场是否从头到尾一致 |
| 理由充分 | 理由是否支撑这个观点，而不是同义反复；有没有往下推一层 |
| 例证具体 | 例子是否有时间、动作、数量这类可核验的细节 |
| 总结呼应 | 结尾是否回到开头的观点，而不是停在例子上 |

### STAR

| 维 | 看什么 |
|---|---|
| 情境交代 | 听的人能否还原出时间、场合、涉及的人 |
| 任务明确 | 有没有说清「要完成什么」，以及难度来自哪 |
| 行动具体 | 是否讲到了动作层面（先找谁、怎么说的），不是「努力协调」 |
| 结果可验 | 有没有结果，以及能不能看出变化（数量、状态、别人的反应） |

### SCQA

| 维 | 看什么 |
|---|---|
| 背景充分 | 听众不了解内情时，能不能听懂后面在讲什么 |
| 冲突成立 | 有没有讲清「为什么现在必须改」，问题感是否真实 |
| 问题收敛 | 冲突有没有收成一个明确的问题，而不是散着 |
| 方案可信 | 方案是否回应了那个问题，代价和收益有没有交代 |

## 引用证据（硬约束）

**任何大于 0 的分数，必须附一句逐字来自用户原话的引用。**

「逐字」的意思是：把那句话复制出来，在用户说过的话里能直接搜到。不能改标点、不能补词、不能换同义词。

```
合格：
  理由充分 1.5
  依据：「因为这样效率更高」
  —— 这句能在原话里搜到

不合格：
  理由充分 1.5
  依据：他认为团队协作能提升效率
  —— 这是你概括的，不是他说的
```

搜不到就两种处理：要么重找一个能搜到的引用，要么把分数降到 0 并说明「这一段没有提到」。

**为什么这么严**：模型很擅长编一句「原文里没有的话」，而用户看不出来——他会以为你听错了，或者以为那句话真是他说的。这是评分失真最主要的来源，不是分数高低的问题。

## 打分结果长什么样

对话里直接说给人听就行，不必输出 JSON。但如果要存档或自检，用这个形状：

```json
{
  "dims": [
    {"label": "情境交代", "score": 3.2, "quote": "我大二的时候在摄影社"},
    {"label": "任务明确", "score": 1.8, "quote": "那次外拍是我负责联系场地"},
    {"label": "行动具体", "score": 2.6, "quote": "跑了十二家店"},
    {"label": "结果可验", "score": 2.4, "quote": "最后来了二十多个人"}
  ],
  "total": 10.0
}
```

存成 `dims.json` 后可以自检：

```bash
python scripts/lint.py score --json dims.json --transcript "用户的原话……"
```

它会查四件事：四维是否齐全、分数是否在 0–4 且一位小数、有分的有没有引用、引用能不能在原话里逐字搜到。**最后一条是这套评分的命门**，也是模型最容易糊弄过去的地方。

## 只讲一件事

复盘一次只讲三样东西：

1. 一句总判断（他这段最突出的问题是什么）
2. 最弱那一维的分数 + 引用 + 一句能落地的改法
3. 让他就这一处重说一遍

不要把四维的优缺点全铺开。四段点评他记不住，也改不动。

---

## 什么时候不给分

- 汉字少于 20 个字：直接说「这段太短，评不出来」，不给分
- 明显跑题：说明跑在哪，不给分
- 完全听不清内容：问一句「刚才那段能再说一次吗」，不给分

**不给分的时候不要编一个低分当安慰。** 0 分和「评不出来」是两件事。

---

## 重说之后

只对比他改的那一处：改前引用什么、改后引用什么、差在哪。**不要重新打一遍四维的总分。** 那会让他觉得前面白说了，也会让两次分数不可比。
